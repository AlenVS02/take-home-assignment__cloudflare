Case 3: Workers not applied

Customer ticket

“I've just added a Worker on the Cloudflare Dashboard for my website: it works in the debugger but doesn't work when I query the site. Why is that? Is there anything to activate or anything I could check?”

Response to the customer

Hello, dear [customer name].

Thank you for reaching out to us regarding the issue you're experiencing with your Worker. I understand that it works in the debugger but not when you query your site, and I'm here to help you resolve this.

To check if the Worker is applied correctly, please follow these steps:

  1. Saving and publishing the Worker: Ensure that you have saved and published the Worker after making any changes. Sometimes, changes may not take effect until the Worker is published, which can be verified in your Worker's Deployments tab.
  2. Attaching your worker to your domain: In your Worker settings, make sure that a route is defined on the <your-domain>.com zone. While the Worker's own address works by itself, it doesn't put the worker on your domain unless you define a route.
  3. The route should match the exact URL you are testing:
    • For example, if your Worker is set to run on <*.your-domain>.com/*, it will apply to all paths under that domain but not your-domain.com.
    • End the pattern with a wildcard (*) to ensure it applies to all paths, such as <your-domain>.com/*, rather than just <your-domain>.com.
    • Ensure that the wildcard (*) is used only at the start and end of the path. Otherwise, in invalid cases like <your-domain>.com/*.jpg, the worker will not be applied correctly.
  4. Review your plan's daily limit: If you are on a free plan, please note that there is a daily limit of 100,000 requests for Workers. If you exceed this limit, the Worker will not be applied until the next day at midnight UTC.

You may confirm that the worker is running in your Worker dashboards by opening the live logs.

  • If no request appears, the request isn't reaching the worker, and you should check the points above.
  • If requests appear with errors, the code is failing on real traffic. This commonly occurs when a secret or variable isn't set in production, or a check on the hostname or path only matched the preview's URL.

A trick you can use to verify whether it ran is to have the Worker attach a header to every response, in the following form:

[url]
  [name]: [value]
This allows you to use the following curl command when testing: 
curl -sD - -o /dev/null https://<your-domain> | grep -i [name]
Lastly, I advise you use a private window when testing to avoid viewing a cached copy of the page.

If the Worker still doesn't apply after these checks, please share the exact URL and the name of the Worker being tested, and I can trace the request from our side.

Best regards,
Alen Valdez Siller,
Cloudflare Support

Thought process

I begin by acknowledging their concerns and their observation about the Worker being invoked in the debugger. This narrows down the issue and indicates that it skips everything real traffic goes through: DNS, routes, deployment state, and plan limits. Saying this reassures the customer and shows to them that the search for the issue is narrowed down.

Since the search for the issue has been narrowed down, we must now verify the three ways a Worker receives traffic.

  • The worker may be saved, but not published which would affect real traffic.
  • Custom domain routes must be defined for the Worker, otherwise, it won't appear.
  • Route matching is essential in assuring that the worker is applied correctly. Since the syntax for routing must be exact, we need to verify that it is not conflicting with or missing any URLs. This is where route patterns can become a common trap for users.

Lastly, so we can split the possible solution into two categories, I suggested that the customer worked with live logs and attaching headers. This is the fastest check for verifying whether the issue is routing-based or code-based.

We empower the customer by giving them tips and tools such as attaching header and verifying live logs, to mitigate repeat incidents and easier debugging on their end.

Tools I would use and why

Where available, I would use the following tools:

  • Cloudflare dashboard: In the Worker Deployments tab, we can view which version is live and whether a deployment is splitting traffic.
  • Worker's Settings: We can verify in the Domain & Routes every route on the zone, including ones with no Worker that exclude a path.
  • Worker Documentation: Consulting the documentation regarding worker usage can help us compare with the customer's implementation and provide proven advise.
  • Account usage: Viewing the usage shows whether the customer has reached their daily request limit.
